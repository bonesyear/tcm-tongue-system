## §1 高优先

### 1. push 凭据链路不可靠 🔴 → ✅ **已解决（2026-09-18）**

> **已解决**：根因是**两层**（都不是"token 不对"），修法与固化见下方「最终根因与修复」。
> 本项保留在此供回溯；下次维护本文件时移入 `REPAIR_PLAN`。

**现象**
```
$ git push origin main
fatal: could not read Password for 'https://***@github.com': No such device or address
```

**证据（实测）**
| 检查项 | 结果 |
|---|---|
| `remote.origin.url` | `https://***@github.com/bonesyear/tcm-tongue-system.git` ← **字面 `***`**，非真 token |
| `GITHUB_TOKEN` 环境变量 | ✗ 未设置 |
| `credential.helper` | 未设置 |
| `~/.git-credentials` | 不存在 |
| token 实际位置 | ✓ `/root/.hermes/.env` |

**根因**：remote URL 里的凭据是**占位符**（不是真 token）；凭据来源在某个时点变过（**具体是哪一步改的，未经证实，不猜**）。

**影响 —— 这是最危险的地方**
- `git commit` ✅ 成功，但 `git push` ❌ 失败
- **两者输出都"看起来正常"** → 极易误以为已推送
- 仓库长期处于「本地领先、远端落后」的**静默分叉**状态
- 本轮就是靠事后 `git log origin/main` 复查才发现

**✅ 最终根因与修复（2026-09-18 实测定位）**

两层原因，**都不是"token 不对"**：

| 层 | 问题 | 修法 |
|---|---|---|
| **①凭证文件格式** | `~/.git-credentials` 写成 `https://<TOKEN>@github.com`（**缺 password 段**）→ `store` helper 匹配失败、**exit 0 但无输出** → git 转去问终端 | 改为 GitHub 官方格式 **`https://x-access-token:<TOKEN>@github.com`** |
| **②全局 URL 重写** | 全局 `~/.gitconfig` 的 `url.insteadOf` 把 `https://github.com/` 重写到 **`https://gh-proxy.com/...`**（第三方镜像，无凭据）| push 时**临时屏蔽全局配置**（不改用户 `~/.gitconfig`）：`GIT_CONFIG_GLOBAL=<临时文件>` |

**诊断线索（关键）**：错误报的是 **`could not read Username`**（不是 Password）→ 这是「凭据 helper 完全没返回值」的特征；且错误里的 host 可能是**镜像域名**（`gh-proxy.com`）→ 指向坑②。

**⚠️ 安全要点**：**绝不能给 gh-proxy 等第三方镜像配置 GitHub token**（等于把 token 交给第三方）。当前 `~/.git-credentials` 只含 `github.com` 条目 → 安全。

**固化**：`scripts/push.sh`（临时屏蔽全局重写 + push + **push 后自动核对本地/远端 SHA**）
**纪律**：`commit` 成功 ≠ `push` 成功，两者输出都"看着正常" → 必须 `git log origin/main -1` 核对。

**建议（已全部落地）**
1. ~~修凭据~~ ✅ 已完成（两层根因均修复）
2. ~~push 后验证纪律~~ ✅ 已写入 skill `public-repo-privacy`
3. ✅ 保留 `scripts/push.sh` 作为标准推送入口

## §2 中等优先

### 2. 非舌诊维度缺基线词条 🟠（用户已跳过）

**现象**：多数指标表**只有异常端词条**，没有正常值词条；正常描述落进"无命中 → 0 分"。

**证据（实测）**
| 指标 | 表内词条 | 正常描述 | 结果 |
|---|---|---|---|
| `nail_color` | 紫暗4 / 暗紫4 / 淡白2 | 红润、淡粉红、淡粉 | 全 MISS → 0 |
| `ear.color` | 红赤3 / 青黑3 / 淡白2 | 淡红、淡红均匀局部稍显红润 | 全 MISS → 0 |
| `face_luster` | 荣润0 / 晦暗5 / 枯槁8 | 有光泽 | MISS → 0 |
| `skin.dryness` | 龟裂6 / 粗糙2 | 无、正常 | MISS → 0 |

**根因**：`_match_score` 的语义是"**命中词条才得分**"，未收录即 0 —— 与"正常=0"**在数值上不可区分**（即 fail-open）。

**影响**
- 结果**大多正确**（正常本就该 0），但机制是"侥幸漏过"而非"明确判定"
- **真正的风险**：一旦出现**未收录的异常表述**，也会被静默算作 0 → **漏报**
- 这正是本轮 `偏胖`、`稍厚` 漏判的同一类问题（已逐个修）

**建议**
- 分维度逐批补**精确基线词素**（`淡红`/`润`/`红润`/`润泽`），**不要**收通用词「正常」（实测长度压制：「正常:0」+「红:3」→「正常偏红」误判 0）
- 优先补有语料支撑的；纯预防性的可延后

### 4. `detail` 的 `mean` 字段名误导 🟠 → ✅ **已解决（2026-09-18）**

> **已解决**：键 `mean` → `score` 改名 + `describe_trend` 加 `metric_name` 参数（非舌维度传「累计分」），
> 落地与回归见 `REPAIR_PLAN` 轮次 10。本项保留在此供回溯；下次维护本文件时移入 `REPAIR_PLAN`。

**现象**
```
手诊 detail: {'mean': 4.0, 'max': 2.0, 'n': 2}   ← mean > max，数学上矛盾
```

**根因（已定位）**
- `compute_dimension_deviation_detail`（`scripts/generate_weekly_report.py:285-290`）的 `mean` 取 `score_dimension(...)`
- 而 `score()` 对**非舌诊维度返回「各指标之和封顶 10」**（`src/scoring.py:395` docstring 明写）
- 手诊两项各 2 分 → **sum 4** > 单项 max 2

**结论**：**不是计算 bug**（sum ≥ max 恒成立），是**字段名与实际语义不符**。

**影响**：任何按「mean ≤ max」做不变量假设的下游消费者都会误报（本轮我就被它绊了一下）。

**建议**（后续轮次）：`mean` → `score` 改名，或 detail 里**额外**给一个真均值字段。注意 `describe_trend` 的双门槛逻辑只用到它的 delta 与 max/n，**改名不影响语义**。

### 5. 点刺判读不稳定 🟠（已定策）

**现象（实测）**：**同一张真实舌照**，Qwen 三次判读：
```
无  →  有（散在轻度红点）  →  有
```
而**用户肉眼确认：无**。

**根因**：点刺（凸起充血的蕈状乳头）与「正常蕈状乳头显影」在**静态照片**上的边界本就模糊，受分辨率/光线/取景角影响；且**对提问方式敏感**（聚焦追问后同一模型就改口）。词表注释（`src/scoring.py:164`）已写明「分辨率敏感 → 分值保守」。

**已定策**：**不加任何结构**（符合「不给不可靠数据建展示位」原则）
- 「**用户肉眼为最终权威**」是唯一生效的安全网
- 低成本改进走 prompt 侧（要求模型输出凸起度/数量/分布依据；存疑输出「不明显」→ 实测自然归零）

**注意**：系统自动识图写入的值**不能直接采信**，需用户确认。

### 7. `tooth_marks: 不明显` → MISS 🟡 → ✅ **不必修（2026-09-18）**

**判定：保持不变**（落空归零本身是正确行为）。

**kimi 的原始意见**（正式表格判为 ✓）：
> 「边缘轻度齿痕→4 ✓、**不明显→0 ✓**」(`kimi_scoring_review2.md:939`)
> 「**不明显 post-neg only applies if keyword present — no keyword → 0 ✓**」(`:647`)
> 同类表态（prickles 的「不明显」）：「在现机制下**都自然归零**（无关键词命中 / 后置否定守卫），**无需改任何结构**」

即：`不明显` 是**后置否定词**，只有**跟着关键词**时才生效（如「点刺不明显」→0）；**单独使用**时没有关键词可命中，自然归零 —— **正确**。

**⚠️ 本文件早期的「可补 `不明显: 0`」提议已被实测推翻**：
```
补「不明显: 0」后：
  轻度齿痕(不明显→轻度)  →  0   ❌ 应为 4
```
根因：`不明显` 是 **3 字**，比 `轻度`/`中度`（**2 字**）**更长** → 最长匹配规则下**它赢** → **把程度词压掉**。
与 §2 的原则冲突：「只收**精确基线词素**，**不收通用词**」—— 「不明显」是否定式短语，且比程度词长，**压制方向相反**。
（对照：`淡红`(2) 压 `红`(1) 是"长压短但方向正确"；`不明显`(3) 压 `轻度`(2) 是"长压短且方向错误"。）

**根本解法**：已由 **#3 的齿痕 prompt 规范化**覆盖（要求模型只输出 无/轻度/中度/重度）。

## §5 知识性「坑」（不是 bug，是判读陷阱）

> 这些是**判读/写档时的陷阱**，详细处理规则见 skill `tcm-tongue-analysis` 与 `tcm-vision-model-strategy`。

| 坑 | 一句话说明 |
|---|---|
| **豆包舌底过度判读** | 系统性把正常浅蓝紫判为"深紫+粗大+蛇形" → **永久忽略豆包舌底结果**；血瘀需深紫+粗大>2mm+蛇形**三合一** |
| **面色虚象链假阳性** | 模型系统性把正常暖白判为"面色淡白/萎黄"；孤立虚象信号**不采信**，须用备用通道交叉核对 |
| **舌中线沟 ≠ 裂纹** | 中央浅纵沟是**生理性正中沟**；判"裂纹"须是深沟/裂开/疼痛 |
| **值夹带判读注记** | 值里写模型名/注记 → 被关键词评分误命中（实测 4 分假阳性）。**值只写当前状态纯描述，注记进 notes** |
| **同名异义：淡紫** | 舌质淡紫 = 异常(6)；舌下淡紫 = 生理正常(0)。**两字段含义相反** |
| **裸「非」不是否定词** | `_NEGATION_RE` = `无|不|未|没|并非|绝非`（有意排除「非」）→「非暗红/紫暗」不被拦截 |
| **同长平局取高分** | fail-loud 设计（宁可高估不漏估）；因此**同一指标内避免同长度正常/异常词并存** |
| **裸「正常」的长度压制** | 「正常:0」(2字) + 「红:3」(1字) → 「正常偏红」误判 0 → **只收精确基线词素** |
| **值禁历史夹注** | 例：「边缘轻度齿痕(前期无明显→轻度回归)」—— 夹注里的"重度"等词会被评分命中（如 7 分高估）。**历史对比放 `lessons`/`*_note`，不进值** |
| **闪光灯禁令** | 舌底/手掌照禁闪光灯（加剧过度判读）|
| **维生素B染尿** | 服药后数小时尿呈亮黄 → 与"小便黄赤"混淆，须先排除 |
| **烟酒急性热象** | 酒精/烟草叠加急性热象（苔黄+咽痛+怕热），须分**急/慢性两层**辨证 |
| **点刺需肉眼** | 点刺/芒刺的凸起度在二维照片上判不准（模型判读会抖）→ **用户肉眼为最终权威** |
| **荣枯/老嫩照片判不了** | 光线干扰大 → 不做展示位，只粗判"干燥/润泽" |
