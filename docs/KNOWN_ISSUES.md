## §1 高优先

### 1. push 凭据链路不可靠 🔴 → ✅ **已解决（2026-09-18）**

> **已解决**：根因是**两层**（都不是"token 不对"），修法与固化见下方「最终根因与修复」。
> 本项保留在此供回溯；下次维护本文件时移入 `REPAIR_PLAN`。

**现象**
```
$ git push origin main
fatal: could not read Password for 'https://***@github.com': No such device or address
```

**证据（实测）**
| 检查项 | 结果 |
|---|---|
| `remote.origin.url` | `https://***@github.com/bonesyear/tcm-tongue-system.git` ← **字面 `***`**，非真 token |
| `GITHUB_TOKEN` 环境变量 | ✗ 未设置 |
| `credential.helper` | 未设置 |
| `~/.git-credentials` | 不存在 |
| token 实际位置 | ✓ `/root/.hermes/.env` |

**根因**：remote URL 里的凭据是**占位符**（不是真 token）；凭据来源在某个时点变过（**具体是哪一步改的，未经证实，不猜**）。

**影响 —— 这是最危险的地方**
- `git commit` ✅ 成功，但 `git push` ❌ 失败
- **两者输出都"看起来正常"** → 极易误以为已推送
- 仓库长期处于「本地领先、远端落后」的**静默分叉**状态
- 本轮就是靠事后 `git log origin/main` 复查才发现

**✅ 最终根因与修复（2026-09-18 实测定位）**

两层原因，**都不是"token 不对"**：

| 层 | 问题 | 修法 |
|---|---|---|
| **①凭证文件格式** | `~/.git-credentials` 写成 `https://<TOKEN>@github.com`（**缺 password 段**）→ `store` helper 匹配失败、**exit 0 但无输出** → git 转去问终端 | 改为 GitHub 官方格式 **`https://x-access-token:<TOKEN>@github.com`** |
| **②全局 URL 重写** | 全局 `~/.gitconfig` 的 `url.insteadOf` 把 `https://github.com/` 重写到 **`https://gh-proxy.com/...`**（第三方镜像，无凭据）| push 时**临时屏蔽全局配置**（不改用户 `~/.gitconfig`）：`GIT_CONFIG_GLOBAL=<临时文件>` |

**诊断线索（关键）**：错误报的是 **`could not read Username`**（不是 Password）→ 这是「凭据 helper 完全没返回值」的特征；且错误里的 host 可能是**镜像域名**（`gh-proxy.com`）→ 指向坑②。

**⚠️ 安全要点**：**绝不能给 gh-proxy 等第三方镜像配置 GitHub token**（等于把 token 交给第三方）。当前 `~/.git-credentials` 只含 `github.com` 条目 → 安全。

**固化**：`scripts/push.sh`（临时屏蔽全局重写 + push + **push 后自动核对本地/远端 SHA**）
**纪律**：`commit` 成功 ≠ `push` 成功，两者输出都"看着正常" → 必须 `git log origin/main -1` 核对。

**建议（已全部落地）**
1. ~~修凭据~~ ✅ 已完成（两层根因均修复）
2. ~~push 后验证纪律~~ ✅ 已写入 skill `public-repo-privacy`
3. ✅ 保留 `scripts/push.sh` 作为标准推送入口

## §2 中等优先

### 2. 非舌诊维度缺基线词条 🟠（用户已跳过）

**现象**：多数指标表**只有异常端词条**，没有正常值词条；正常描述落进"无命中 → 0 分"。

**证据（实测）**
| 指标 | 表内词条 | 正常描述 | 结果 |
|---|---|---|---|
| `nail_color` | 紫暗4 / 暗紫4 / 淡白4（2026-10-16 升）/ 红润0（2026-10-20 补基线） | 淡粉红、淡粉 | MISS → 0 |
| `ear.color` | 红赤3 / 青黑3 / 淡白2 | 淡红、淡红均匀局部稍显红润 | 全 MISS → 0 |
| `face_luster` | 荣润0 / 晦暗5 / 枯槁8 | 有光泽 | MISS → 0 |
| `skin.dryness` | 龟裂6 / 粗糙2 | 无、正常 | MISS → 0 |

**根因**：`_match_score` 的语义是"**命中词条才得分**"，未收录即 0 —— 与"正常=0"**在数值上不可区分**（即 fail-open）。

**影响**
- 结果**大多正确**（正常本就该 0），但机制是"侥幸漏过"而非"明确判定"
- **真正的风险**：一旦出现**未收录的异常表述**，也会被静默算作 0 → **漏报**
- 这正是本轮 `偏胖`、`稍厚` 漏判的同一类问题（已逐个修）

**建议**
- 分维度逐批补**精确基线词素**（`淡红`/`润`/`红润`/`润泽`），**不要**收通用词「正常」（实测长度压制：「正常:0」+「红:3」→「正常偏红」误判 0）
- 优先补有语料支撑的；纯预防性的可延后

**补充（2026-10-26，B04）**：新 `assess*` 已让未命中文本返回 `unknown`，不再于新页面/趋势中静默按正常 0 展示；旧 `score*` 为兼容仍返回 0。基线词表补全与真实模型标定仍未完成，故本项保留为部分缓解而非关闭。

### 4. `detail` 的 `mean` 字段名误导 🟠 → ✅ **已解决（2026-09-18）**

> **已解决**：键 `mean` → `score` 改名 + `describe_trend` 加 `metric_name` 参数（非舌维度传「累计分」），
> 落地与回归见 `REPAIR_PLAN` 轮次 10。本项保留在此供回溯；下次维护本文件时移入 `REPAIR_PLAN`。

**现象**
```
手诊 detail: {'mean': 4.0, 'max': 2.0, 'n': 2}   ← mean > max，数学上矛盾
```

**根因（已定位）**
- `compute_dimension_deviation_detail`（`scripts/generate_weekly_report.py:285-290`）的 `mean` 取 `score_dimension(...)`
- 而 `score()` 对**非舌诊维度返回「各指标之和封顶 10」**（`src/scoring.py:395` docstring 明写）
- 手诊两项各 2 分 → **sum 4** > 单项 max 2

**结论**：**不是计算 bug**（sum ≥ max 恒成立），是**字段名与实际语义不符**。

**影响**：任何按「mean ≤ max」做不变量假设的下游消费者都会误报（本轮我就被它绊了一下）。

**建议**（后续轮次）：`mean` → `score` 改名，或 detail 里**额外**给一个真均值字段。注意 `describe_trend` 的双门槛逻辑只用到它的 delta 与 max/n，**改名不影响语义**。

### 5. 模型点刺判读不可靠：抖动 + 系统性偏向判「有」 🟠 → ✅ **已解决（2026-09-18）**

**现象（实测）**：

- 早期：同一真实舌照三次判读 `无 → 有（散在轻度红点）→ 有`，用户肉眼确认「无」。
- **2026-09-18 采样稳定性实验（同一张真实舌照，9 次调用）**：新 prompt 不传 temperature ×3、新 prompt temperature=0 ×3、旧 prompt ×3 —— **点刺 9/9 判「有」**，而用户肉眼 = 「无」。即 9-17 A/B 那次 Qwen 判「无」是**少数采样命中，不是稳定能力**（9-17 A/B 报告已归档删除；结论以本节与 9-18 档案 `ab_test_note` 为准）。
- **跨图复测（实验 2，同日）**：取该用户另一张舌面照（历史档案 8-09 的舌面图），`temperature=0` ×5 → **5/5 判「有」**。两图合计 **10/10**，即对「有散在红点的舌面」**一致报「点刺」，无输出不确定性**。
  ⚠️ **局限**：两图均属「有散在红点」情形，故只证明**对该用户一致判有**，**不能**证明「判有率与真值完全无关」（后者需「真值有 + 真值无」对照；8-28 真值疑似「有」的照片已丢失）。
  **术语层根因（本次识图自查新发现）**：VLM 的判据是「**有没有红点**」而非「**红点是否凸起增大**」，而舌尖/舌边**正常蕈状乳头本身就呈红点状**（生理现象）→ 系统性假阳性。这解释了为何 10/10 稳定判有——不是随机抖动，是**判据错位**。
- **温度真相（2026-09-18 查明，推翻本节「temp=0」框架）**：本节实验条件中所写的 `temperature=0` **从未真正生效**——DashScope 官方文档（`qwen-api-via-dashscope`）明确：qwen3.8-max（思考模式）**视觉理解的 temperature 默认为 0.6，0.6 以下的值会被服务端默认改为 0.6**（取值范围 `[0, 2)`）。即传 0 与不传参**完全等价**，原「temp=0 不解决点刺/不解决抖动」的表述把温度当作一次失败的干预——**但它根本不是一次有效干预**，该推论形式失效。**修正后结论**：点刺 10/10 判有**与采样温度无关**（该端点温度无可辨效应）；抖动与偏向的主源是**判据错位 + 服务端不确定性**。**实验 1（同日）**：同图 temp=0 vs temp=1.0 各 10 次、交叉交替（共 20 次），9 个字段众数全一致；评分层仅 temp=0 组齿痕 3/10、厚薄 2/10 不稳（temp=1.0 组全稳），双侧 Fisher p≈0.21/0.47 均不显著——两组无可辨差异，与钳制规则吻合（实际比较的是 0.6 vs 1.0，且结构化输出的尖峰分布使温度效应本就微小）。⚠️ 准确表述是「**0.6 以下被钳制到 0.6，故 0 与默认等价**」，**不得概括为「temperature 无效」**（0.6 以上参数仍生效，只是对该任务效应微小）。payload 已改为显式写 `0.6` 如实反映生效值（`scripts/vision_client.py`）。

**根因**：点刺（凸起充血的蕈状乳头）的**凸起度**需触诊/动态观察，与「正常蕈状乳头显影」在**静态照片**上边界模糊，受分辨率/光线/取景角影响，且对提问方式敏感。

**核心洞察（本次新发现）**：v1.4.2 的点刺规范化句「不填『少量』『散在』『不明显』等描述性短语」**拆掉了安全阀**——旧机制下模型犹豫时可输出「不明显」由否定守卫自然归零（#7 已确认是正确行为）；强制三选一后，系统性偏向无处对冲，直接落成 **5 分假阳性**。规范化句解决了 MISS 漏判（#6），却把「自我对冲的不确定」变成了「硬假阳性」。

**处置（已落地，d + b 组合）**：

- **d. 退出评分层、降级到辨证层** ✅：凸起度静态照片不可判，不满足 `src/scoring.py:139-143` 的收录原则（「评分层只收静态照片可客观判读的指标」），同 #18 `palm_temp` 先例。`prickles` 从 `DIMENSION_RULES[TONGUE]` 移除；词表 `TONGUE_PRICKLES_MAP` 保留备查（含 `少量: 2` 兜底语义记录）；**档案 `prickles` 字段（用户肉眼值）继续保留供辨证层使用**，只是不参与数值评分。⚠️ 结构变化：舌诊维度少一项，历史偏离度不可直接比较（#17 历史不追溯原则）。

- ⚠️ **实测：安全阀效果微乎其微（2026-09-18，同图 6 次）**：

  - **4/5 次未输出 `点刺依据` 键**（模型不遵从"输出两个键"的要求）；

- → **这反向强化了 d 方案的正确性**：该字段不是靠改 prompt 能救的，**处置不变**（退出评分层 + 肉眼签认）。
- → **教训**：「跑通」保证**结构合规**，**不保证模型遵从**（对模型的三令五申未必被遵守；`点刺依据` 键的缺失即为证）。

**根因**：`trends_store` 总是显式注入旧分类函数，报告层又覆盖调用方函数；共享根复制未按启用类别过滤；统一候选未按类别拆分；未知目录用默认类别代替真实归属。

**影响与处置**：B26 让正式入口默认进入统一视图，显式注入原样保留；共享根在检索前剔除未启用类别，混合根中专类专用根优先；每类只保存本类候选。三类齐全时未分类综合资料标为 `composite` 通用候选并单独输入，缺类时无法确定归属则 fail closed。全量 **1046 passed、1 skipped**，真实源库各模式差分一致，停用方剂候选为 0，源文件字节不变。

**建议**：检索与报告验收必须覆盖真实 Web 包装器，不只直接调用底层函数；共享根、专用根和通用综合资料应分别验证，不能靠默认类别维持表面兼容。

### 38. 临时视图重复构建与进程崩溃残留 ⏸（2026-11-04）

**现象**：每次分类根报告仍重新复制并构建 RAG；强制结束进程会留下临时副本。B27 已清理正常及异常请求后的缓存，但未消除重复构建和强退残留。

**建议**：B28 再评估按规范根与版本复用受管视图、同版本并发构建锁、原子发布和有界清理，只清理由系统创建的可识别目录。另合并本文件重复的 #34 登记，不新增同号项。
