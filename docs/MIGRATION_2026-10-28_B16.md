# B16 恢复语义、照片与数据生命周期（v1.13.9）

**日期**：2026-10-28
**范围**：F55、F56、F58、F59、F62、G4、G28。仅改变文件与数据生命周期，不改变医学权重、红线、评分或剂量策略。

## 1. 用途备份与当前代恢复

`web/lifecycle_store.py` 管理快照。`records/_backup/.index.json` 记录用途、UTC 时间和单调递增序号，恢复不再按本地墙钟或文件名字典序判断“最早”。普通备份按每天最多 20 份保留；pristine 和当前撤销所需快照优先保留，旧格式文件只在本批新增索引之外保留，不自动删除。

每次向导提交写入 `pristine_snapshot`，包含快照 ID、用途、序号与 UTC 时间。旧记录首次修正时也补建该指针。报告生成、修正、向导和恢复分别使用 `report/correction/wizard/restore` 用途。

`恢复/撤销` 的语义：

- 首次恢复读取**当前代修正前 pristine**，不跨回上一代识图结果。
- 当前 `diagnosis.report` 与结构化结论保留；其输入指纹决定是否过期，不静默删除模型报告。
- 恢复前写 `restore` 安全备份；再次执行可撤销最近一次恢复，回到恢复前状态。
- 快照缺失或记录不存在时失败，不凭旧备份复活已删除记录。
- 没有新指针的旧格式记录只作最近快照的兼容兜底，不宣称能辨认历史世代。

## 2. 图片清洗与发送边界

`web/photo_store.py` 使用项目已有的 Pillow：

- 请求和单图上限 **20 MiB**，像素上限 **40,000,000**；超限请求返回 413 或可诊断 400。
- 只接受真实 JPEG/PNG/WebP，拒绝伪造扩展名、损坏图片与异常像素，不再直接保存任意字节。
- 按 EXIF Orientation 重排像素，再编码为不带 EXIF/GPS/设备元数据的 JPEG。
- `vision_client.call` 对 CLI 图片也执行清洗；Web 暂存图已清洗，不重复压缩。模型只收到清洗后的 JPEG 字节，MIME 统一为 `image/jpeg`。

这些措施不替代用户检查照片内容本身，也不宣称医学判读已经标定。

## 3. 暂存、提交与回滚

上传写入 `records/photos/<日期>/.staging/`，而不是直接覆盖 `<部位>.jpg`：

- 识图失败、模型未配置或取消提交时，已提交原图不变，清洗图保留在暂存区，响应带 `staged=true`。
- 只有本轮真实识图的部位可在成功提交时转正。merge 跳过已覆盖维度时，不替换其照片。
- 转正把同部位旧图及旧扩展名移入 `records/_backup/photos/<日期>/`，提交冲突时恢复旧图与暂存图。
- 新记录以 `photos: {部位: 文件名}` 显式绑定。详情页和 `/photos` 只提供当前登记图片，旧扩展名、暂存和跳过部位的遗留文件不混入原图对照；无绑定字段的旧记录保留目录兼容。
- 照片绑定纳入报告输入指纹；重分析保留报告并由指纹标记过期。

## 4. 删除与保留策略

新增管理员专用 `POST /record/<date>/delete`，请求必须明确携带 `confirm=DELETE`。详情页提供展开式确认区和原生 POST 表单，浏览器确认只是辅助，服务端仍强制确认。

按日期删除：

- daily 记录与 `.wizard-<date>.json*` 草稿；
- 当日普通/pristine/restore 备份及索引条目；
- `photos/<date>/` 正式图、暂存图和对应照片备份。

删除后恢复入口仍要求当前记录存在，不会用残留快照复活。损坏草稿改为带 UTC 与随机后缀的独立 `.corrupt` 文件，后续损坏不再覆盖旧证据；隔离失败也会告警。

普通 JSON 备份按每日 20 份保留，pristine 与当前撤销快照不被普通数量清理误删。按日期删除是显式永久操作，不自动创建“待删除”备份。
