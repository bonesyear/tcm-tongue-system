# #21 记录与草稿并发写冲突检测（v1.13.1）

**日期**：2026-10-27
**状态**：已修复应用内 JSON 记录与向导草稿的并发读－改－写丢更新；未改变医学记录结构、评分、预警或报告内容。

## 原因与修复

原子替换只能避免半截文件，不能阻止两个请求读取同一旧版本后依次覆盖。现在每次读取同时取得文件内容的 SHA-256，写入前在同目录 `.write.lock` 内再次比较；不一致则抛出 `WriteConflictError`，不替换目标文件。

`web/io_utils.py` 提供：

- `read_versioned_json()`：从同一次字节读取得到 JSON 与版本，避免内容和哈希来自两个版本。
- `file_version()`：返回当前内容哈希；文件不存在返回 `None`，因此“要求原文件不存在”与“未提供版本”不同。
- `write_lock()`：同目录可重入的线程/进程写锁；Windows 使用 `msvcrt`，POSIX 使用 `fcntl`。独立锁文件不会随目标原子替换而失效。
- 带可选 `expected_version` 的 `atomic_write_json()`、`atomic_write_text()` 与 `remove_file()`。旧调用接口保留；生产记录/草稿写路径均显式传入读取版本。

临时文件仍在失败时清理。锁文件只作同步，不包含医学数据，运行时不要用删除锁文件来解除冲突。

## 覆盖路径

- 记录修正与恢复：`records_store.update_observation()`、`restore_original()`。
- 辨证报告：模型调用前取得版本，调用期间不持锁；返回并校验后按该版本写回，期间发生的修正不会被旧报告覆盖。
- 向导草稿：字段修正、手动录入、问诊、上下文、照片识图、跳过全部携带版本。
- 向导提交：在同一 `write_lock(daily_dir)` 内先核对记录和草稿，再备份、写记录、删除草稿。任一版本变化都不写记录、不删草稿。

旧 `load_record()` / `load_draft()` 保持原返回契约；需要写入的生产路径使用新增的 `load_record_with_version()` / `load_draft_with_version()`。不向医学 JSON 写入锁版本字段，也不要求前端表单增加令牌。

## 用户可见行为

API 冲突返回 HTTP 409、`ok=false`、`conflict=true`，并同时提供 `error` 和 `errors` 兼容现有页面。提示为“文件已被其他操作更新，请刷新后重试”。上下文表单冲突回到向导的现有错误区。

跳过、问诊选择和清空问诊以前忽略失败响应，现均显示错误。冲突后应重新读取最新内容再操作；系统不自动合并，也不把失败响应当成功。

## 验证与边界

- 全量测试 **666 → 678 passed**。
- 线程与 Windows spawn 独立进程使用同一旧版本竞争时，只有一个写入成功，另一个得到冲突；最终文件对应成功写入者。
- 真实 Flask 路由覆盖修正、恢复、报告、草稿和提交冲突；提交失败保留记录与草稿，正常重试成功。
- 两个不同字段的记录修正竞争后，失败方重新读取可保存，最终两项修改均保留。
- 向导内联脚本 `node --check` 通过；治理清单 157 项校验通过。

本批保护应用内 JSON 写入，不处理照片同名覆盖、外部编辑器绕过应用直写或离线自动合并。Windows 已完成线程与进程实测；POSIX `fcntl` 路径未在本机实机验证。未读取真实健康记录、照片或 `.env`，未调用真实模型。
