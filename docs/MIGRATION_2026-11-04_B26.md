# B26 正式报告链路与缺类隔离（v1.20.16）

**日期**：2026-11-04
**范围**：修复统一知识库视图审查中确认的正式入口绕过、共享根缺类越界、自定义注入失效和分类溯源失真。保留模块化与统一检索方案，不修改知识库正文、医学规则、评分、权重或剂量策略。

## 1. 审查发现

- 正式 Web 路由经 `trends_store.generate_and_store_report()` 显式注入旧分类检索，统一视图在真实包装器中的调用次数为 0；此前测试只直接调用底层报告函数。
- 两类共享综合根时复制整个根，停用方剂后的完整报告仍出现一条方剂候选。
- 传入的自定义 `kb_references` 被默认函数覆盖；统一模式下每类又保存同一份全量候选，导致溯源失真和记录膨胀。
- 未按专类目录组织的共享文件被默认标为体质，但既有系统同时支持三类共用任意布局的综合库，不能简单全部拒绝。

## 2. 修复内容

- `trends_store` 默认传递 `kb_references=None`，让正式路由进入统一检索；调用方显式提供的函数原样转发并走原分类路径。
- 共享根在复制前按相对路径识别类别，未启用类别的文件不进入临时视图、RAG、候选或模型输入。混合根中，某类已有专用根时，共享根中的该专类文件不再参与。
- 每类 `kb_categories[category].refs` 只含本类候选，状态按本类实际命中设置；完整 `kb_refs` 保持统一全局预算，不复制成三份送入模型。
- 统一视图中的候选必须有明确来源；未登记来源的命中明确报错，不再回退为体质。

## 3. 任意布局综合库的兼容语义

专类目录继续为 `diagnostics/`、`diet-lifestyle/`、`formulas/`。专用根中的 `notes/` 等普通目录按导入时声明的类别处理，不受本次共享根规则影响。

三类全部可用时，共享综合根中无法归入专类的文件标为 `composite` 通用候选，单独进入模型输入，不再冒称体质。缺少任一类别时，这种文件无法排除被停用内容，统一检索明确报错、关闭本次候选，并由现有报告状态与输出闸门披露。`composite` 只是候选溯源标记，不是第四类知识库或新的导入类别。
